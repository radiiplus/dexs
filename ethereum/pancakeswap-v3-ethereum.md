## Architecture and execution map

- `PancakeV3Factory.createPool` sorts tokens, validates fee-tier enablement and optional allowlist state, and delegates CREATE2 construction to `PancakeV3PoolDeployer`. The deployer temporarily stores constructor parameters; the resulting pool stores factory, token pair, fee, tick spacing, and per-tick liquidity bound as immutables. Pool initialization is permissionless and one-time.
- The pool stores `slot0` price/tick/oracle/fee protocol state, active liquidity, initialized tick and bitmap state, position fee checkpoints, global fee growth, protocol fee balances, observations, and an optional LM pool. Mint, burn, collect, swap, flash, oracle growth, and protocol fee actions are lock-guarded where they mutate pool state. Swap and mint callbacks occur while locked and must settle the exact required token balance increase or the transaction reverts.
- `SwapRouter` derives pool addresses from the trusted deployer and sorted `(token0, token1, fee)` key. Exact-input routes pay through callbacks and chain intermediate outputs; exact-output routes recurse through callbacks in reverse path order, cap input, and require full output when no custom price limit is set. `NonfungiblePositionManager` maps ERC-721 token IDs to pool/tick ranges, manages pool liquidity, checkpoints fee growth, and collects principal and fees.
- Pancake's LM hook calls `accumulateReward` at swap start and `crossLmTick` when initialized ticks are crossed. The associated LM pool restricts those calls to the pool/masterchef. The factory owner controls protocol fee settings and pool LM-pool installation; this is privileged configuration, not a pool accounting defect.
- Invariants reviewed: each swap's token deltas reconcile with pool balance changes; input payment is verified after callbacks; initialized tick crossings update active liquidity and fee/oracle outside accumulators consistently; LP fee growth excludes protocol fee shares; protocol fee balances track amounts separated from LP fees; mint/burn/collect update position principal and fee claims without transferring an unbacked balance; router paths preserve payer/recipient settlement; any callback, slippage, limit, or payment failure rolls back all intermediate state.

## Entry points and transitions reviewed

- Factory and deployer: supported fee and tick-spacing state, whitelist controls, pool-key ordering, pool initialization, CREATE2 derivation, protocol fee forwarding, and LM pool registration.
- Pool: initialize, observation growth, mint callback, position checkpoint, burn and principal debt, collect, exact-input/output swap steps, tick bitmap traversal/crossing, oracle writes, protocol fee accounting, flash loan reconciliation, fee collection, and LM callbacks.
- Periphery: canonical V3 `SwapRouter` exact-input/output single and multihop paths, callback validation and payment source; `NonfungiblePositionManager` create/increase/decrease/collect/burn, per-token fee checkpoints, approvals, and NFT ownership transfer.
- LM integration: reward timestamp accumulation, reward growth by LM liquidity, initialized LM tick crossing, and pool/masterchef caller restrictions.
- Token assumption: standard ERC-20 exact transfer semantics. Fee-on-transfer and rebasing tokens are not treated as supported unless separately handled by an integration.

## Findings

No confirmed implementation defect was identified in the sampled Ethereum pool family, shared core accounting, canonical V3 router, or position manager paths reviewed.

### Rejected hypothesis: callback execution can interleave pool state updates

Pool mutators enter under `lock`; swap sets `slot0.unlocked=false` before external LM and token callbacks and restores it only after balance settlement. Mint and flash are also locked across callbacks. A callback attempting a nested locked pool operation reverts, and any failure rolls back both pool state and token transfers. Read-only calls may see in-transaction intermediate state, but no reachable second settlement path was established.

### Rejected hypothesis: protocol fees and LP fee growth are double-counted

During swap steps, protocol fees are removed from `step.feeAmount` before adding the residual to global LP fee growth. The same protocol portion accumulates in the input token's `protocolFees` balance and is transferred only through authorized `collectProtocol`. Flash fees similarly separate protocol and LP shares after exact pre/post balance reconciliation. The sample pool currently has a nonzero protocol-fee configuration; read-only configuration is a snapshot and may be changed by factory governance.

### Rejected hypothesis: NFT position and core pool claims can drift during liquidity changes

The manager keys core positions by `(manager, tickLower, tickUpper)` and keeps per-NFT liquidity/fee checkpoints. Increase and decrease operations update the core position then checkpoint fee growth using the pre-operation NFT liquidity; collect first pokes the core position with zero-liquidity burn when active, calculates accrued fees, caps amounts to owed balances, and subtracts the nominal amount collected. ERC-721 transfer preserves the token ID's associated accounting and changes authorization owner. No sequence was found that can withdraw more than the NFT's principal and accumulated fee claims.

Other examined boundaries did not yield a credible candidate: tick bounds and spacing are checked; negative tick compression rounds toward negative infinity; bitmap traversal is clamped to protocol min/max ticks; per-tick gross liquidity is capped; fee and square-root math use checked or full-precision helpers in the relevant ranges; observation and cumulative counters intentionally wrap at their documented widths; failed output/input limits revert the whole callback sequence.

## Validation and limitations

- No custom regression test was written or run because no credible defect candidate remained. The repository's existing test suites were not run.
- Read-only calls confirmed sample token order, factory, fee tier/tick spacing, pool registration, current liquidity, protocol fee snapshot, and the official factory/pool deployer addresses. No live swap, mint, collect, or vulnerability test was performed.
- Scope is the canonical Pancake V3 core plus canonical V3 router and position-manager implementation family. The mixed-protocol Smart Router, farming/masterchef reward distribution beyond pool hook authorization, other chains, and nonstandard token behavior require separate review.
