# Cross-Chain Research Options

Screening snapshot: 2026-11-26. This is a target-selection note, not a security finding. GeckoTerminal and DeFiLlama indexes are discovery sources; TVL and volume values are time-sensitive and do not establish source correctness, a vulnerable path, or profitability. No conclusion from an Ethereum implementation is transferred to another chain.

## Selection Criteria

- A substantial DEX surface, including less-studied implementations and active pools.
- Independent lending, liquidation, auction, or settlement systems with live capital.
- EVM fork feasibility where possible; non-EVM chains remain separate tracks with their own state acquisition and test harnesses.
- Exact deployed source/runtime, accepted asset, and reachable payout must be established before proposing a loop.

### Synthetic JLP liquidation overlap scenario (local fork probed; loop not closed)

This remains a conditional scenario, not a vulnerability finding or evidence that an attacker can cause the modeled price move. I installed Surfpool 1.8.0 under `/tmp` and used it as a local, lazy Solana mainnet fork. All state changes below were confined to Surfpool; no public transaction was submitted.

- The forked state for vault 8 position `9377` decoded to `121.77096484` JLP and `357.213984939` USDC debt at the read slot. The Chainlink JLP/USD answer was `3.65493478` (8 decimals), which gives an SDK-calculated debt/collateral ratio of `80.26%`, below the `90%` threshold. The Perps read API returned a JLP price of `$3.6478` during this pass.
- Holding that position's debt and collateral constant, an oracle answer of `$3.2163` (about a `12.00%` decline) gives a modeled ratio of `91.21%`. This is a synthetic threshold crossing, created only by changing the local fork's Chainlink account through Surfpool.
- The SDK-built USDC flashloan plus vault-wide liquidation instruction executed the flash borrow at zero fee. At the unmodified feed price, liquidation reverted with `VAULT_INVALID_LIQUIDATION` (`6027`). At the synthetic lower price, the builder's remaining accounts omitted tick accounts required by the on-chain loop; adding the existing local tick accounts `708` through `702` let the liquidation instruction progress to flashloan repayment. The transaction then reverted with SPL `insufficient funds` because no JLP redemption was included. Omitting flashloan payback instead reverted with `FLASHLOAN_PAYBACK_NOT_FOUND` (`6009`). These simulations did not establish that position `9377` itself was selected or fully liquidated, nor did they produce a realized JLP amount or profit.
- Jupiter's Perps burn API built a read-only unsigned JLP-to-USDC transaction for a public wallet, but fractional burn requests returned HTTP 500 and the larger scaled request returned HTTP 422. I did not complete a remapped burn instruction in the local transaction, so the liquidation-to-redemption-to-repayment loop remains untested end to end.
- Source check: the inspected Jupiter oracle adapter calls Chainlink `read_feed_v2` and consumes `latest_round_data`; that adapter does not reject the feed's `FLAGGED` header state. The forked feed had state `1` (`FLAGGED`). This is an observation requiring confirmation of intended semantics and exact deployed source/runtime, not a finding by itself. The forked programs were not bytecode-matched to the pinned source commit in this pass.
- Let `R` be USDC repaid, `p` the effective collateral incentive, `P_o` the liquidation oracle price, `P_x` the executable JLP exit price, and `C` all swap, compute, and transaction costs. If the liquidation transfers collateral worth `R * (1 + p)` at `P_o`, then modeled net is `R * (1 + p) * (P_x / P_o) - R - C`. At equal oracle and exit prices this is `R * p - C`; break-even requires `P_x / P_o > (1 + C/R) / (1 + p)`.
- Conditional economics using figures supplied in the discussion, not independently refreshed or confirmed: with `p = 3%`, `R = $10,000`, `C = $0.50`, `P_o = $3.645286`, and `P_x = $3.646035`, the formula gives about `$301.62` net. At price parity it gives `$299.50`; break-even is `P_x/P_o > 0.970922`, or an exit discount smaller than about `2.91%`. These figures assume the full 3% is paid to the liquidator and the modeled amount can be exited at the stated price; they are not realized results. Jupiter documents zero-fee flashloans and describes liquidation incentives as vault-specific, intended liquidator compensation ([flashloans](https://developers.jup.ag/docs/lend/flashloan), [liquidation](https://developers.jup.ag/docs/lend/borrow/liquidation)). A flashloan reduces upfront capital needs but does not improve return per dollar repaid; the transaction still incurs network fees.
- The supplied aggregate `$147.7M` vault debt times 3% is `$4.431M` gross arithmetic, but this is not an estimate of available profit. It assumes every dollar of debt is liquidatable and receives the full bonus, which is not established. The number of positions (`9,741`) does not identify liquidatable debt. Jupiter's read interface exposes position risk ratios, but no current eligible-position amount, per-position liquidation cap, or realized exit has been verified here ([read vault data](https://developers.jup.ag/docs/lend/borrow/read-vault-data)). Therefore total realizable profit remains unknown.
- The published oracle docs list freshness limits of 600 seconds for user operations and 7,200 seconds for liquidations, while noting Chainlink freshness is slot-based. This general asymmetry does not prove that the vault 8 JLP oracle can supply a stale-low price on the relevant path; the exact source configuration, feed state semantics, and resulting liquidation eligibility still need deployment-matched validation ([oracle freshness](https://developers.jup.ag/docs/lend/oracles)). JLP APR alone does not establish price volatility or recurring liquidations.
- The liquidation penalty, exact seized JLP amount, borrower selected by vault-wide liquidation, and executable Perps output remain unconfirmed. The earlier `85.59%` sample and `5.5%` threshold estimate were stale/inconsistent with this fork read and should not be reused. No profitable closed loop has been reproduced.

This scenario has a real cross-protocol topology but does not currently show an attacker-controlled discrepancy or profit. If Perps NAV and the lender oracle both fall together, any liquidation bonus is ordinary protocol behavior; a distinct loop requires an independently reachable oracle/exit-price mismatch and a local simulation that redeems the actual seized JLP and repays the flashloan atomically.

## Recommended Order

1. BNB Chain Lista Smart Lending: stopped for current profit-loop work at the PublicLiquidator gate. Reopen only if an independently verified permissionless payout path becomes reachable or a distinct unprivileged settlement consumer is identified.
2. BNB Chain Venus/PancakeSwap: continue only after an exact pair/collateral or settlement-path overlap is found.
3. Solana Jupiter JLP: verify flagged-feed semantics and SDK tick-account assembly, then complete the local burn/repay simulation; no profit is confirmed.
4. Base, Arbitrum, Optimism, Avalanche, Monad, and Sui: stop broad review until an exact discrepancy-to-market edge appears. Re-run the index filter after new candidates are identified.

No candidate here is yet a confirmed defect, reproduced invariant violation, or profitable loop. Lista's exact LP-collateral overlap is real, but the current public payout gate fails and the deployed pool implementation is not matched to the available source. The BNB fork call reproduced the gate revert. The Jupiter local fork executed the flashloan borrow and reached liquidation under a synthetic feed override, but the end-to-end unwind and repayment did not complete.
