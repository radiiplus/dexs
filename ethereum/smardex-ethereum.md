## V1 architecture and transitions

- `SmardexFactory.createPair` sorts tokens, deploys a V1 pair with CREATE2 and records both lookup orders. The pair exposes LP ERC-20/permit, `mint`, `burn`, `swap`, `skim`, reserve/fictive-reserve and moving-average views. `swap` is lock-protected, computes exact-input or exact-output amounts through the V1 library, transfers output, invokes the caller callback, measures input settlement, then updates fictive reserves and the price average.
- The reserve invariant is `token balance - feeToAmount` for each token; V1 accumulates protocol fees in `feeToAmount` and settles them to `feeTo` during mint/burn. LP mint/burn scale virtual reserves with supply changes and distribute actual token balances pro rata. The V1 and V2 accounting implementations are not treated as interchangeable.

## V2 architecture and transitions

- `SmardexFactory` owns fee and whitelist settings, creates V2 pairs after whitelist closure, or registers existing nonempty pairs while the whitelist is open. It stores `feeTo`, default `feesLP`/`feesPool`, and both token-order lookups. Owner-set fees must have nonzero LP fee and a combined rate no greater than `FEES_MAX`.
- `SmardexPair.swap` reads actual balances net of fee ledgers, updates the EMA using the prior fictive reserves and a maximum 300-second observation interval, quotes via `SmardexLibrary.getAmountOut/In`, optimistically transfers output and invokes the callback. It then checks measured input against the required delta, accrues the pool share into `feeToAmount` when protocol fees are enabled, and stores new fictive reserves. The lock covers external token and callback calls.
- `mint`/`burn` settle existing fee ledgers first, then use observed balances and LP supply to mint shares or pay pro rata. Mint callbacks must deliver at least both requested token amounts. V2's `feeTo` contract is called after the locked liquidity transition to process accumulated fees; its failure is intentionally ignored, while pair accounting remains in the pair until later processing.
- V2 invariants reviewed: reserve views equal actual token balances less outstanding protocol fee ledgers; fee liabilities remain backed and leave only through fee settlement or an explicit fee-off transition; LP shares track the pool's actual balances and proportional fictive reserves; swaps meet callback payment requirements and update EMA/virtual reserves atomically; failures revert all in-transaction transfers and state.

## Findings

No confirmed implementation defect was identified in the sampled V1 or V2 source families.

### Rejected hypotheses

- **V2 protocol fee callback can fail after mint/burn:** `_feeToSwap` is deliberately best-effort. The pair records fees separately before unlocking; a failed AutoSwapper call does not erase the amount, and subsequent fee handling can retry. This was not an unbacked balance or user-settlement discrepancy.
- **Fee ledger is double-counted in swap settlement:** the pair subtracts the pre-existing fee ledger to derive tradable reserves and separately includes that ledger in the post-callback minimum-balance check. Newly accrued protocol fee is added only after that check, leaving the measured user input and fee liability backed by the same token balance.
- **V1/V2 factory changes imply shared invariants:** they have distinct fee configuration, reserve synchronization, fee settlement, and pair code. No V1 conclusion was used to establish V2 behavior or vice versa.
- **EMA timestamp/price state can be stale within a block:** the library intentionally caps elapsed time and reuses the prior price state at the same timestamp; swap quote and state update use the same calculated average. No accounting violation was established from this expected oracle update policy.

## Validation and limitations

- No local regression was written because no credible invariant violation remained. No state-changing public deployment call was made. Read-only factory, pair, reserve, fictive reserve, price-average, and V2 fee configuration reads were used only to establish target identity and a current snapshot.
- This assessment covers the cited V1 and V2 pair/factory families and the cited V2 router/AutoSwapper paths. It does not claim every GeckoTerminal pool or all auxiliary reward, staking, cross-chain, or frontend contracts were reviewed. Deployment configuration and current proxy status were not independently established as universal properties.
