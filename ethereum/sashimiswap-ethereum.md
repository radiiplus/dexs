## Architecture and execution map

- `UniswapV2Factory.createPair` sorts token addresses, requires a nonzero `_router`, deploys `UniswapV2Pair` with CREATE2, initializes its token and router fields, and records the pair in both token orders. The factory constructor sets `feeToSetter`; that address controls `feeTo`, `migrator`, and replacement of `feeToSetter`. The factory has no proxy.
- Pair LP token supply, balances, reserves, cumulative prices, `kLast`, and lock state are held in each pair. `mint`, `burn`, `swap`, and `sync` are lock-protected. Pair `_getBalance(token)` reads `router.getTokenInPair(pair, token)`, not `IERC20(token).balanceOf(pair)`. Consequently, pair reserves track router-side per-pair ledger values, not tokens held at the pair address.
- Router `_transferIn` transfers user tokens to the router and credits the actual received delta to `_pools[pair][token]`. `_transferOut` debits this ledger and transfers from router custody or withdraws from its configured vault. Liquidity entry points credit the ledger before pair `mint`; removal has the pair burn its LP tokens and reduce the ledger before the router pays both assets. Swaps transfer input into router custody, decrement the output ledger, increment the next hop's ledger for multi-hop routes, then call pair `swap` to verify and update reserves.
- The router can keep assets invested in its vault while exposing balances through `_pools`. This means pair invariant checks are compositional: they trust the exact router address set at pair creation to report the ledger and settle outbound assets. An incorrect router binding can make a pair's accounting unusable even where the factory, pair, and ordinary V2 arithmetic are individually valid.

## Entry points and invariants reviewed

- Factory pair creation, token sorting/duplicate checks, router initialization, fee and migrator administration, pair binding, and CREATE2 deployment.
- Pair initialization, LP transfer/permit, mint, burn, ordinary swap/callback, `sync`, reserve bounds and timestamp/cumulative prices, and `kLast` fee minting.
- Router add/remove liquidity, fee-on-transfer removal, exact-input and exact-output swaps, multi-hop settlement, ledger custody transitions, vault withdrawals, `getTokenInPair`, and quote math.
- Invariants reviewed: pair reserves equal the selected router's per-pair ledger after every successful update; incoming transfers credit the actual received amount; outgoing payments debit ledger value once; multi-hop output is removed from the prior pair and credited to the next pair; mint and burn share changes use the same logical balances used by reserve accounting; adjusted swap balances satisfy the pair's fee-adjusted product check; and any failed nested settlement rolls back the enclosing transaction.

## Findings

### SASHIMI-ETH-1: Unrestricted one-time router initialization can permanently brick a new factory

- **Status:** Confirmed source-level initialization defect; reproduced locally. The sampled deployed factory is already initialized and its sampled pair uses the intended router, so no current exposure is established for that existing deployment.
- **Severity:** Low. The impact is limited to a race before the legitimate router is assigned. A new factory can be abandoned and redeployed, but the setter cannot be repaired once a nonzero address wins.
- **Evidence:** In the verified factory source, `setRouter(address)` only requires `_router == address(0)` and has no caller authorization. By contrast, adjacent `setFeeTo`, `setMigrator`, and `setFeeToSetter` each require `msg.sender == feeToSetter`. `createPair` refuses to run until `_router` is nonzero and permanently passes `_router` into each pair's `initialize`. The pair then uses that router for every balance read. See [factory source](https://eth.blockscout.com/address/0xf028f723ed1d0fe01cc59973c49298aa95c57472#code), [pair source](https://eth.blockscout.com/address/0x2b773b3db41971c069f79c257ab60bdc8bd1ae5f#code), and [router source](https://eth.blockscout.com/address/0xe4fe6a45f354e845f954cddee6084603cedb9410#code).
- **Pre-state:** A newly deployed factory has `_router == address(0)`, and no pair can be created yet. Any caller may invoke `setRouter` first with any address, including an EOA or incompatible contract.
- **Transition:** The first nonzero value is stored permanently. The intended deployer or fee setter cannot replace it because the same zero-value guard now fails. New pairs bind the selected address. With an EOA or nonconforming router, calls such as pair `mint`, `burn`, `swap`, or `sync` cannot obtain the expected `getTokenInPair` ledger; use of the intended router also cannot reconcile its own `_pools` with the pair's bound router.
- **Invariant/impact:** Every pair's reserve accounting and settlement must use the router that owns the matching ledger and custody path. An arbitrary caller can win the initialization race and make all subsequently created pairs use a router that does not meet that invariant. This is a permissionless, factory-wide denial of service during bootstrap, not a demonstrated theft of existing pool assets.
- **Deployment boundary:** The sampled live pair currently returns router `0xe4fe6a45f354e845f954cddee6084603cedb9410`; the factory's router slot itself is private, but this pair was initialized by the factory and provides a direct snapshot of its configured router. Existing created pairs cannot be changed by this setter. This report does not establish that the live deployment was ever vulnerable to a race, nor that the selected router is malicious.
- **Regression:** [Local regression](sashimiswap-router-initialization.test.js) compiles the exact verified factory source with Solidity `0.6.12` and optimizer 200, deploys it in an in-memory Ganache chain, and asserts that an unprivileged first caller's router is irrevocable, is copied into the next pair, and makes `sync()` revert when the bound router is an EOA. Result: PASS. No live transaction was sent.
- **Remediation:** Accept the router in the factory constructor, restrict initialization to `feeToSetter` or a dedicated deployer, and/or use a two-step initialization where the authorized setter confirms the address. Emit a router-set event and provide a guarded recovery path only if the protocol intends the router to be upgradeable.

## Rejected hypotheses

- **Pair token balance differs from ERC-20 balance at the pair address:** This is intentional architecture. The router holds tokens and tracks per-pair balances; pair mint/burn/swap read that same router ledger, and router settlement changes the ledger before the pair verifies its invariant. The pair is not expected to custody the underlying tokens directly.
- **Router output debit temporarily precedes the pair swap check:** This is the settlement design. The router pays output and decrements its ledger before pair `swap`; the pair then derives input from the post-output ledger and checks the constant-product invariant. A failed pair call reverts the prior ledger and token transfers atomically.
- **Pair initializer lacks an initialized flag:** Only the fixed factory address can invoke `initialize`; the factory exposes it only inline with creation of a fresh pair and has no method to reinitialize an existing pair.
- **Unrestricted `setRouter` currently changes deployed pools:** It cannot; it is one-shot and the sampled pair already shows a nonzero router. Existing pair bindings are immutable through the factory interface.

## Validation and limitations

- The isolated regression used the exact verified factory compiler input and ran only on a local in-memory EVM with synthetic token addresses. It demonstrated the setter race and permanent lock-in, not token theft or live deployment impact.
- No state-changing interaction was made with public deployments. Read-only source and getter evidence anchor the sample. No claim is made about every SashimiSwap pool, token behavior, farming/reward contract, vault strategy, or future deployment.
- The historical public repository does not contain the matching core source, so findings are based on the verified deployment-independent factory, pair, and router source. The source URLs above should be used for future verification if the repository adds or updates the core implementation.
