## Architecture and execution map

The Vaults IDL exposes `operate_dex`, `operate_perfect_dex`, `liquidate_dex`, `liquidate_perfect_dex`, `rebalance_dex`, and `rebalance_dex_with_amounts`. The DEX IDL exposes deposit/withdraw and borrow/payback variants, plus `swap_in` and `swap_out`. The SDK builders assemble the Vaults instruction, DEX pool and position accounts, Liquidity reserve/position accounts, oracle accounts, and tick/branch setup instructions. Successful fork logs show Vaults `OperateDex` invoking DEX `Borrow` and Liquidity `Operate`/`PreOperate` paths.

The reviewed state topology has a particularly useful native overlap:

- DEX pool 3 (`DQfkVMGvZzqdq5jwoCRAyD26rJEioPM6kRGjC7BYts5P`) is enabled for both smart collateral and smart debt. It trades `JuprjznTrTSp2UFa3ZBUFgwdAmtZCq4MQCwysN55USD` against USDC, uses six decimals on both sides, and has a configured 1% fee.
- Vault 108 is T2: pool 3 shares are collateral and USDC is ordinary debt.
- Vault 91 is T3: the ordinary collateral mint is `59obFNBzyTBGowrkif5uK7ojS58vsuWz3ZCvg6tfZAGw`, while pool 3 shares are smart debt.
- Both Vaults therefore consume the same DEX pool state through different lending roles. This is topology evidence, not a finding.

## Invariants under review

1. A Vault's DEX supply or borrow share position should move consistently with the corresponding DEX pool share total, subject to documented fees and integer rounding.
2. A Vault's aggregate supply and debt accounting should reconcile with its DEX-side position after conversion into the Vault/Liquidity accounting units.
3. A swap can change DEX reserves and the stored price, but should not silently mint or burn lending or DEX position shares.
4. A user operation, its DEX CPI, token transfers, and Vault position updates should be atomic: a failed leg must leave no partial accounting transition.
5. Rebalance and liquidation conversions should use compatible DEX share and oracle valuation rules. These paths remain unverified because their deployed handler source is not public in the pinned materials.

## Assessment and next checks

**Confirmed implementation defects:** none.
**Reproduced invariant violations:** none.
**Plausible but unverified risks:** exact conversions used by smart-vault liquidation and rebalancing; the relationship between `dust_debt_amount`, DEX borrow shares, and Vault aggregate debt under repeated small operations; and behavior when a swap crosses configured utilization or oracle/price boundaries.
**Expected behavior observed:** pool swaps move stored price without moving DEX share totals; smart supply/withdraw update the DEX and Vault supply totals equally in the tested T2 sequence; T3 borrowing moved aggregate DEX and Vault debt accounting by nearly identical normalized amounts.

Rebalance is gated by each Vault configuration's rebalancer authority and was not exercised with an unauthorized signer. Liquidation was not tested because no controlled unhealthy synthetic position was established. Flash liquidity was not needed for these native operation tests. The next source-dependent work is to acquire a deployment-matched DEX/Vaults smart-handler build or a full source release, then verify the one-unit rounding observation and test exact-share liquidation/rebalance transitions against independently decoded account states.

## Reentrancy screen

Solana's runtime changes the relevant threat model: direct self-recursion (`A -> A`) is allowed, but indirect reentry (`A -> B -> A`) fails with `ReentrancyNotAllowed`. This blocks the ordinary callback cycles `Vaults -> DEX -> Liquidity -> Vaults` and `DEX -> Token-2022 -> transfer hook -> DEX`. Deeper CPI nesting does not remove that rule ([Solana CPI rules](https://solana.com/developers/docs/core/cpi)). The DEX program also has a per-pool `Dex.re_entrancy` field; all 11 decoded live `Dex` accounts had it clear at the finalized read, and Jupiter's current [DEX CPI documentation](https://developers.jup.ag/docs/lend/dex/cpi.md) says a second same-pool swap during the active instruction fails with `DexAlreadyEntered` (6017).

For the current vault 99 / DEX pool 8 overlap, both mints are owned by the classic SPL Token program, so there is no Token-2022 transfer-hook callback in the concrete path. Other live DEX pools include Token-2022 mints. Two successfully decoded mints expose a TransferHook extension with a zero hook-program address at the read; a third account read was inconsistent across RPC requests and is not used as evidence. No active malicious or unexpected hook was established.

**Assessment:** I found no reentrancy blindspot that closes into a callback cycle for the current Jupiter Lend/DEX path. The app-level pool lock is not a substitute for source review, but the runtime blocks indirect reentry even if a token hook is configured. A remaining, different question is cross-program ordering: a hook may call an unrelated program during token transfer without re-entering the active DEX; whether that matters depends on the exact token's hook configuration, CPI privileges, and whether the called program reads transient shared state. That is unverified and is not classified as a vulnerability. The deployed DEX and smart-Vault handlers remain closed source in the reviewed repositories, so I cannot claim the DEX lock covers every DEX instruction from source alone.

## Accepted-input intersection: mutable Token-2022 transfer fees

The interface/state map exposes a narrower configuration intersection than callback reentry:

| Boundary | Accepts | Rejects / guard |
|---|---|---|
| DEX token program | Classic SPL Token and Token-2022 program accounts | Invalid mint/program pairings produce DEX token validation errors |
| Liquidity reserve mint initialization | Token-2022 `TransferFeeConfig` extension | Shared library rejects a mint if either old or new transfer-fee basis points is nonzero; it also rejects a configured transfer-hook program |
| Liquidity supply credit | Incoming transfer with actual vault balance delta at least equal to `operate_amount_in` | Rejects a shortfall, and rejects overage above the configured 1% bound |
| Active DEX pool 7 | Token-2022 mint `2u1tszSeqZ3qBWF3uNGPFc8TzMk2tdiwknnRMWGWjGWH` paired with USDC; smart collateral is enabled | At the read, both transfer-fee schedules had 0 bps and 0 max fee; transfer-hook program ID was zero |

The intersection is that the mint's transfer-fee configuration authority is nonzero and can change the schedule after the Liquidity reserve passed its initialization-time extension check. The shared source validates the extension in `liquidity/src/module/admin.rs` during reserve setup, but the inspected runtime `operate` path instead relies on the balance-delta bound. The live DEX program-data ELF was fetched and its SHA-256 matches the earlier pinned value `81a37033b308eb4fcc4ec4ebfb644bc5cbc1c9f262a2063cb3f38202337e54c7`; the DEX handler itself remains unavailable as source.

This creates a conditional cross-layer loss path in the lending markets, not just a possible swap failure. The same USDG mint is the debt asset of active Borrow vaults including vault 6 (WSOL collateral, 684 positions), vault 10 (JLP collateral, 170 positions), and vault 14 (JupSOL collateral, 795 positions); it is also token0 in active DEX pool 7. The public market API reports substantial outstanding USDG debt in these vaults. The mint's transfer-fee config authority and withheld-fee authority are both nonzero and equal; current old/new fee rates are zero.

If that authority schedules a nonzero fee, then after activation a borrower repayment or liquidator payment for nominal debt `A` is transferred through Token-2022 with gross amount `A`, while the receiving account gets `A - fee`. Vaults' liquidation source transfers `actual_debt_amt` into its borrow-token account and then asks Liquidity to pay back that same amount. Liquidity checks the actual vault balance increase and requires it to be at least `operate_amount_in`; the source check is lower-bounded at the full requested amount. The transfer shortfall therefore makes repayment/liquidation fail atomically unless some path explicitly grosses up and reconciles the transfer, which the reviewed Vaults and Liquidity source does not show. If debt positions become unhealthy while this persists, lenders can be left with unliquidated debt and eventual collateral shortfall. Token-2022 also permits the withheld authority to collect fees from destination token accounts; fee activation is delayed by two epochs, not immediate.

**Classification:** a credible privileged configuration-to-liveness-to-credit-loss chain, not a permissionless DEX exploit and not a confirmed current loss. It requires the USDG transfer-fee authority to act, the fee to become nonzero, borrowers/liquidations to touch the affected debt reserve, and positions to remain impaired long enough for collateral recovery to be insufficient. Current transfer fees are zero. Whether a protocol guardian can pause markets, reject repay transactions safely, or otherwise remediate the transition was not assessed. The DEX-specific output-side handling (`amount_out_min` versus net received) also remains unknown because the deployed DEX handler source is unavailable.

A decisive local test would mutate the synthetic fork mint to a nonzero transfer-fee schedule, then attempt a normal USDG repayment and liquidation through the active vaults while observing transfer deltas, Liquidity reserve balance checks, rollback, and position/debt state. Separately test DEX `swap_in`/`swap_out`, deposit, and borrow for gross requested input, net output, share deltas, and slippage checks. Do not infer exploitability by an unprivileged caller: the fee-setting authority is a required privileged actor.

## Artificial position-impairment screen: USDG debt vaults

I checked whether a third party can move USDG-borrower positions across their liquidation boundary by changing a DEX spot price or another caller-controlled input. The current public Borrow API lists 11 USDG debt vaults. Their collateral pricing routes are Chainlink for WSOL, JLP, cbBTC, xBTC, WBTC, and syrupUSDC; Chainlink plus stake-pool exchange rates for JupSOL, JitoSOL, and LBTC; a Marinade pool rate plus Chainlink for mSOL; and four JupLend fToken exchange-rate hops for jlJUPUSD. None of those configured source lists is a direct DEX spot-price source.

The pinned Oracle source reads the configured Chainlink account's `latest_round_data`, checks its publish slot against the Solana clock, then uses the answer. The caller cannot substitute an arbitrary account because the Oracle state stores the configured source and `verify_source` checks the supplied remaining accounts against it. Chainlink thus is not a writable price parameter for an ordinary borrower, liquidator, or DEX trader. No evidence was found that a trade in Jupiter's local DEX can write or directly alter the configured Chainlink feed account.

There is a meaningful timing asymmetry: the Oracle constants allow up to 600 seconds for operate pricing and 7,200 seconds for liquidation pricing; Chainlink freshness converts slot difference to time using a fixed 400 ms per slot. Vaults use the shorter operate price for borrowing/withdrawal risk checks and the liquidation price for liquidations; deposit/repay safety checks also use the liquidation price. Therefore a stale-high collateral feed can delay liquidation while market value has fallen, and a stale-low feed can expose positions to premature liquidation. This depends on a real feed update delay or a mismatch between feed value and recoverable collateral value; a user cannot force Chainlink to publish an old or chosen answer. It is a market/oracle availability condition, not a demonstrated attacker-controlled impairment primitive.

The non-Chainlink legs do not currently close an artificial price-down path either. Stake-pool and mSOL source handlers calculate collateral-to-SOL exchange rates from on-chain pool balances and supply, with fee/refresh guards on the stake-pool path. The jlJUPUSD source reads lending/reserve/rate-model/mint accounts and computes an fToken exchange price; the pinned helper rejects a decrease in the underlying Liquidity exchange price and applies accrued rewards/interest to the stored exchange price. This makes a temporary DEX spot move insufficient to lower the configured collateral rate. Whether a native staking pool can suffer a governance-driven rate reduction or actual solvency loss is an issuer/protocol risk and was not established as caller-controlled here.

One compositional hypothesis was that a large jlJUPUSD deposit could increase fToken supply, lower the rate model's per-asset rewards rate, and make the oracle apply that lower rate retroactively to time since the last checkpoint. The pinned Lending source does not support that sequence: `deposit_internal` first updates Liquidity, calls `update_rates` using the current fToken supply, then mints shares; `withdraw_internal` updates rates before burning shares. That checkpoints accrued rewards against the pre-transition supply and starts the next interval after the supply change. A same-transaction deposit/liquidation/withdraw therefore cannot make the oracle reprice the already elapsed interval using a transient supply denominator. This candidate is **disproven at the source level for the public Lending deposit/withdraw paths**; exact deployed matching and a local regression were not performed.

The more concrete Chainlink blindspot is shared dependency, not caller control. The current USDG vault API snapshot shows the same SOL/USD Chainlink source in vaults 6 (WSOL), 14 (JupSOL), 16 (JitoSOL), and 48 (mSOL): 1,910 positions and about 1.080 billion raw USDG debt (approximately $1.08 million at six decimals). The same BTC/USD feed is shared by vaults 12 (cbBTC), 17 (xBTC), 26 (WBTC), and 44 (LBTC): 366 positions and about $1.356 million raw USDG debt. The liquid-staking vaults also multiply this common USD price by a separate stake-pool exchange rate. Those source paths are not independent price observations; a single source's stale or erroneous answer can shift liquidation eligibility across multiple collateral types at once. This concentration can amplify a genuine feed or market incident, but is not itself an attacker-writable impairment primitive.

**Disposition:** I found no supported route for an unprivileged DEX trader to artificially mark an existing USDG position unhealthy through the configured oracle sources. The useful blindspot is narrower: the two-hour liquidation freshness budget can preserve stale collateral valuation much longer than the ten-minute borrow/withdraw budget. It can contribute to lender loss if a genuine collateral value decline occurs during a delayed-feed interval, but the attacker-controlled trigger is not established. Current API observations showed equal operate and liquidation prices for the listed USDG vaults; that does not prove future freshness or price correctness. No local feed mutation or liquidation simulation was run in this pass.

## Native share / underlying peg intersection: JUICED collateral

The current Borrow API exposes a more relevant cross-layer pricing assumption in vaults 68, 69, and 70. All three accept jlJUPUSD (JUICED) as collateral, with USDC, USDT, and USDG debt respectively; each oracle configuration consists of the same four-account JupLend fToken source group and contains no JupUSD/USD market feed. The pinned Oracle handler computes the JUICED-to-JupUSD exchange rate. Jupiter's current integration documentation then explicitly defines JUICED value as `exchange_rate * JupUSD price ($1)`. Thus the lending valuation follows the share exchange rate while the underlying peg assumption is supplied as a constant, not read from a market price.

This is a useful accepted-input intersection because ordinary holders can deposit JupUSD to mint JUICED and use the shares as collateral, but direct JupUSD mint/redeem is restricted to registered benefactors. Public holders therefore depend on secondary markets for exit; the JUICED integration documentation also describes withdrawal limits that smooth large outflows. A sufficiently impaired JupUSD market or redemption path could make recoverable collateral worth less than the Borrow oracle's share value. A market discount alone does not prove loss: issuer redemption, liquidity recovery, and liquidation proceeds must be accounted for.

At the latest read on 2026-11-27, the API listed 1,894, 816, and 74 positions in vaults 68/69/70, with debt of about $466.3k USDC, $38.5k USDT, and $1.1k USDG. Each has an 89% collateral factor and 91% liquidation threshold; all three currently report zero borrowable capacity. The JUICED API reported about $38.16m total assets and $2.62m immediately withdrawable under its current liquidity limit. JupUSD was quoted near par: the JupUSD-to-USDC route returned about 0.99954 USDC per JupUSD for a 1m-token quote, and top JupUSD/USDC pools were near $1. No current discount approaches the level that would make a new max-CF position undercollateralized; before costs, that requires the recoverable JupUSD value to fall below roughly 89% of the assumed $1 price, with additional margin needed for fees, sale impact, and liquidation costs.

**Candidate classification:** conditional peg-risk composition, not a confirmed code defect or current profitable loop. It could contribute to lender bad debt if JupUSD's recoverable value falls materially while JUICED's oracle remains at exchange-rate-times-par, and if the vault has capacity when a position is opened. Current capacity is zero in all three Borrow markets; current market price is near par; public secondary liquidity exists. The documented 2-hour Chainlink liquidation age is not part of this JupLend source path, so it should not be attached to this candidate. No local stress simulation has been run.

## T2 DEX collateral / hard peg configuration: USDGO vault 105

A finalized on-chain decode found VaultConfig 105 even though the Borrow API omitted it. It is type T2: collateral is DEX pool 11 (USDGO/USDC), debt is USDC, collateral factor 92%, liquidation threshold 94%, and liquidation max limit 96%; VaultState reports 18 positions. The pinned Vaults source documents stored values in tenths of a percent (`900 = 90%`), and the live config returns `920/940/960`. Pool 11 has smart collateral enabled and smart debt disabled. Its oracle account uses `DexSmartColPegOracle`; the referenced `DexPegOracleConfig` points to pool 11, has `conversion_source = Pubkey::default()` (IDL semantics: hard 1:1 conversion), and stores raw `peg_buffer_percent = 5,000` in the current decoded account. The IDL does not document this field's scale, so no percentage interpretation is asserted. This is a direct native DEX-share/lending intersection rather than an external price consumer.

The config and IDL expose several distinct acceptance boundaries. The oracle config binds the DEX, position-token accounts, and both reserve accounts; the default conversion source treats the two underlying tokens as a 1:1 pair. The VaultConfig permits a 92% collateral factor, 94% liquidation threshold, and 96% liquidation max. The `liquidate_dex` interface takes `col_per_unit_debt`, an `absorb` flag, and optional collateral output amounts. The stripped Vaults and Oracle ELFs contain reserve/config mismatch, zero-reserve, invalid-buffer, liquidation-amount, and excess-slippage errors, but the exact predicates and accepted ranges are not recoverable from the public source or the disassembly reviewed so far. The public Fluid snapshot has no `DexSmartColPegOracle`, `operate_dex`, or `liquidate_dex` implementation. The public Borrow API omits this T2 vault, so its raw VaultState totals (supply shares `3999896730135941`, borrow shares `6755314587190577`) cannot safely be interpreted as USD or used to estimate borrow capacity without matching exchange-price and DEX-share conversion logic. Absorbed debt/collateral were both zero at the read.

The published `@jup-ag/lend` 0.4.0 client adds a separate, client-side acceptance map. For imperfect DEX operations it rejects mixed-sign token legs, rejects an all-zero token leg when shares are nonzero, and rejects `i128::MIN`; for perfect operations the IDL explicitly reserves `i128::MIN` as a max-withdraw/max-payback sentinel. The SDK also constrains perfect token min/max bounds to `|bound| <= u64::MAX` because its code says the program casts those bounds to `u64`. The `liquidate_dex` SDK builder accepts any supplied BN for `colPerUnitDebt` without a client-side bound, while the IDL encodes it as `u128`; deployed high-bit/narrowing behavior remains unknown. The client checks are not assumed to be the contract's checks; the local runtime boundary results are in the probe sections below.

A read-only SDK reconstruction of position IDs 1 through 18 found nonzero debt on IDs 1, 2, 3, and 10; its derived liquidation-status flag was false for all 18. This is not an on-chain risk-status API and does not prove the Vaults handler would reject liquidation under every state transition, but it provides no current liquidatable position to use for a live-state settlement test.

### Local range probe

Surfpool 1.8.0 was started as a local mainnet fork at slot 474395413. Using synthetic USDGO/USDC token balances set only in Surfpool, an `operate_dex` supply-plus-borrow simulation for vault 105 completed successfully with the SDK's recommended 1.4m compute-unit limit. The Oracle log emitted `smart_col_exchange_rate: 1998229941988276`; the binary's scale for this logged value is not independently established here. No transaction was submitted to mainnet and the simulated state was not committed.

The same fork tested the imperfect smart-collateral `shares_min_max` boundary with otherwise-valid deposit inputs. `u64::MAX` passed the Vault conversion and reached the DEX, where it reverted with `DEX_SHARES_MINTED_LESS` because the supplied floor exceeded minted shares. `u64::MAX + 1` and `u64::MAX + 2` reverted earlier in the Vault with `LIBRARY_CASTING_ERROR` at deployed source path `programs/vaults/src/utils/dex.rs:216`. This confirms a checked upper-bound conversion for this specific `OperateDex` field and disproves unchecked high-bit truncation on that path. The SDK rejected mixed-sign supply amounts and imperfect `i128::MIN` before producing an instruction; the hand-crafted runtime results are below. The `absorb` flag remains untested. The liquidation probe below accepted and dispatched the `col_per_unit_debt` boundary values but did not reach their final slippage comparison because the current account state is not liquidatable.

### Liquidation optional-account and u128 boundary probe

The SDK's `getLiquidateDexIx` builder supplies the vault's Liquidity supply-position PDA for this T2 vault even though that PDA does not exist on mainnet and the IDL marks `vault_supply_position_on_liquidity` optional/not required for T2. The first local simulation failed Anchor account validation with `AccountOwnedByWrongProgram` (3007), before instruction logic. Replacing that meta with the Vaults program ID (Anchor's optional-account `None` sentinel) passed account validation, ran the Oracle CPI, and reached the Vaults liquidation handler. This is a client account-construction issue in the tested SDK path; it is not evidence that the deployed handler itself requires the nonexistent T2 account.

With the optional account absent, I simulated `col_per_unit_debt` values 0, 1, `u64::MAX`, `u64::MAX + 1`, and `u128::MAX`. Anchor/Borsh instruction decoding returned each exact input value, including the high 64-bit word and the all-ones 128-bit value. Every run then failed identically with deployed error 6027, `VaultInvalidLiquidation`, before a successful liquidation or slippage comparison. The existing positions in vault 105 are healthy at the forked state, so this result does not establish whether high bits are narrowed, checked, or compared correctly after eligibility succeeds. The `u128` acceptance boundary remains unresolved; no liquidation or asset movement occurred.

The runtime log reports `programs/vaults/src/state/structs.rs:537` for error 6027, while the pinned public source at that path and commit has no error expression at that line. This location string therefore cannot be used to attribute the deployed handler to the pinned source snapshot. The deployed ELF hash and fork identity remain the evidence for which bytecode was simulated; no source-to-bytecode match is claimed for the missing smart-vault handler.

### Imperfect signed-input and perfect sentinel probe

To bypass only the SDK's input validation, I decoded a valid local `operate_dex` instruction, changed its serialized `OperateDexAmounts`, and re-encoded it through the pinned Anchor/Borsh coder. The hand-crafted mixed-sign input (`token0 = -1`, `token1 = 1`) reached the deployed program and reverted with `VaultInvalidOperateAmount` (6009). `token0 = i128::MIN` reached the dedicated `VaultOperateDexImperfectMaxUsePerfect` guard (6082). `i128::MIN + 1` and `-2^64` reverted with `VaultInvalidOperateAmount` (6009). No token movement survived any failed simulation. This confirms that the runtime rejects the same imperfect mixed-sign and sentinel cases the SDK rejects; it does not silently reinterpret the high sign bit as a small amount.

The paired perfect-path test committed a synthetic 1,000,000-raw-unit deposit of each USDGO/USDC token to a fresh position on the local Surfpool fork, then simulated a `max: true` one-token withdrawal. The instruction decoded `perfect_shares = i128::MIN`, entered DEX `WithdrawPerfectInOneToken`, and succeeded. The simulated USDGO account balance was unchanged; the USDC balance rose by 1,999,848 raw units, returning the position's roughly 2,000,000 raw units of par-valued collateral through the selected one-token exit. The observed 152-raw-unit difference is not isolated to a specific fee or rounding component; it is not a profit or material loss path.

For the perfect token bound, a hand-crafted `token1_min_max = -u64::MAX` passed Vault conversion and reached the DEX, which rejected the impossible minimum with `DexWithdrawalNotEnough` (6037). `token1_min_max = -(u64::MAX + 1)` failed in the Vault with `LibraryCastingFailure` (6001) at the checked conversion. This verifies that the deliberate `i128::MIN` full-exit sentinel is distinct from token bounds and that the tested 64-bit narrowing boundary is checked.

### Cross-leg perfect max: smart collateral withdrawal plus normal debt payback

To test an intersection of individually valid operations, I opened a local T2 position with 1,000,000 raw units of each USDGO/USDC supplied as smart collateral and 1,000,000 raw USDC borrowed as ordinary debt. In a second local transaction, `operate_perfect_dex` applied `max` to both legs: withdraw all DEX collateral into USDC and repay the full ordinary debt. The SDK-built instruction succeeded. The position moved from `supply_amount=995877580`, `dust_debt_amount=119240`, `tick=-3` to zero supply, zero debt, and the cold tick. The signer's USDGO balance stayed at 9,999,000,000 raw units; the USDC balance increased by 999,847 raw units after repayment. No residual Vault debt or collateral remained.

I then swept the DEX collateral output minimum around the observed withdrawal. `token1_min_max=-1,999,848` succeeded. `token1_min_max=-1,999,849` failed with `DexWithdrawalNotEnough` (6037). The rejected simulation reverted as a whole; no partial state was committed. This maps the exact one-unit slippage boundary for this state and shows the DEX output guard rejects an overlarge minimum before the combined operation can settle. It does not create a profit loop or reveal an accounting mismatch; the small net difference is consistent with token conversion/rounding and accrued debt, but has not been attributed to a single component.

The results disprove the suspected high-bit truncation on these two tested operation fields; no wider claim is made for unrelated fields or program instructions.

The market is currently close to parity: GeckoTerminal reports USDGO/USDC at 0.999956, about $8.15m reserve value, and $18.1k 24-hour volume. Its matching finalized reserve-exchange-price read corresponds to approximately 4.075m USDGO and 3.958m USDC; a Jupiter quote for 1 USDGO returned 0.999856 USDC with 0.0044% price impact. That is no present impairment. The important intersection is conditional: the oracle configuration converts both reserve assets at 1:1, while a real sale or redemption could value USDGO below USDC. Under the simplifying model that a collateral share owns pro-rata reserves `x` USDGO and `y` USDC, the configured oracle values it at `x+y`, while realizable value at USDGO price `p` is `p*x+y`. At the 92% collateral factor, an initial max-factor position would be asset-underwater before costs when `p < 0.92 - 0.08*(y/x)`. For vault 105's observed reserve mix, that is about `p < 0.842`; equal reserves would require `p < 0.84`. This assumes the oracle continues to value both tokens at par through a depeg and the collateral claim is pro-rata; neither is verified from the stripped deployed handler. The exact share valuation, peg-buffer scale/behavior, and health/liquidation predicates remain unresolved. If the oracle does continue using the configured 1:1 conversion, that discrepancy could also keep an account from crossing the oracle-based liquidation threshold while actual recovery value is below debt. That state transition has not been reproduced.

The next validation is to obtain a locally controlled liquidatable position in a smart-collateral vault, then repeat the liquidation boundary sweep and compare debt reduction with both withdrawn tokens. In parallel, map which pool reserve compositions and peg deviations the oracle accepts, which oracle risk ratios `operate_dex` accepts for borrowing, and whether `absorb` uses the same health calculation or a separate shortfall calculation. Do not infer a profitable loop from the current market snapshot: USDGO is near parity, and T2 borrow capacity/risk is not exposed by the public Borrow API.

### Mutable Token-2022 fee / recipient-minimum mismatch

The exact USDGO mint in DEX pool 11 is Token-2022 and has a nonzero transfer-fee config authority (`8N2NFYQ5VMaoDGMAcUbfzdeJqvok6LQs2E9BxDK6mMAE`). Its currently decoded older and newer fee schedules are both 0 bps, so this is not a present fee loss. The mint also has a transfer-hook extension whose program ID is the System Program, so this candidate does not depend on an active transfer hook. The pinned Vaults type docs explicitly define negative `operate_perfect_dex` token bounds as minimum tokens to receive. The tested smart-collateral withdrawal instead satisfies that bound against gross withdrawal output, not the recipient's net balance delta.

I used a separate local Surfnet fork of the local mainnet fork. First, a synthetic T2 position deposited 1,000,000 raw USDGO and 1,000,000 raw USDC while fees were 0 bps. A no-fee simulation of a max withdrawal measured gross outputs of 1,014,566 raw USDGO and 985,427 raw USDC. I then changed only the child fork's USDGO mint account to an active 100-bps transfer-fee state using Surfpool `setAccount`, and simulated the same withdrawal with those exact gross outputs as the minimums. The Vault/DEX instruction succeeded. The user's USDGO balance increased by only 1,004,420 raw units, 10,146 below the specified 1,014,566 minimum; USDC increased by 985,427 as specified. Raising only the USDGO minimum to 1,014,567 made the DEX revert with `DexBelowWithdrawMin` (6030). This establishes that the tested DEX guard compares gross withdrawal amounts while Token-2022 delivers a smaller net amount to the recipient.

With that same synthetic fee state, a separate new USDGO smart-collateral supply failed in Liquidity with `TransferAmountOutOfBounds` (6033) after the Token-2022 transfer. The Vault/DEX CPI then failed and the simulation committed no state. The input-side balance-delta guard therefore rejects this net-short deposit instead of minting shares against the nominal amount. The verified asymmetry is output slippage protection versus input accounting; repayment is expected to follow the same source path but was not separately simulated.

**Classification:** reproduced conditional recipient-slippage mismatch in deployed Vault/DEX bytecode on an isolated fork; current schedule is 0 bps, and no live transaction or fee-authority operation was performed. The local test directly changed the child fork's mint account to isolate runtime behavior; it did not reproduce the authority-signed fee-scheduling instruction or its activation delay. A token authority can create the state transition, so the impact is conditional on a privileged mint configuration change. In that state, a user relying on the documented minimum can receive less than requested, with the difference withheld by Token-2022. This is not a permissionless protocol drain and does not establish attacker profit. The deployed DEX source is unavailable in the pinned public repository; the runtime result is bytecode evidence, and the intended net-output semantics come from the pinned Vaults type documentation.

Regression artifact: [jupiter-lend-fee-phase-probe.mjs](jupiter-lend-fee-phase-probe.mjs), run with `npm ci && npm run test:fee-phase` while `JUPLEND_FORK_RPC` points to a local fork. It asserts the output-bound mismatch and reports the input-side 6033 rejection. The harness creates a child Surfnet, so its mint mutation and synthetic position do not modify the parent fork. Its pinned research-only dependency set reports npm audit advisories; it is not intended for production use.

**New composition concept:** treat token extensions as mutable protocol state, not a one-time token property. Intersect (1) initialization-time acceptance with a zero fee, (2) later extension-state mutation, (3) a DEX output guard over gross amounts, and (4) a recipient's net balance delta. The validated case finds a slippage guarantee gap; it does not yield a closed profit loop. This same lifecycle-phase screen should now be applied to deposits, repayment, swaps, and withdrawals in other DEX pools that accept Token-2022 mints with mutable extensions.
